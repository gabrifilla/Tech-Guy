## 3. Approved control scheme

### Movement

- WASD: direct character movement.
- Mouse cursor: independent combat aiming.
- Space: dodge/dash.
- Character orientation and movement restrictions must respect the active attack, skill, recovery, and animation contracts.
- An attack must not automatically allow unrestricted movement if its existing design requires commitment.

The existing click-to-move model is to be replaced during the future control migration.

The movement implementation must not introduce a second movement controller or duplicate navigation authority.

The proposed use of NavMeshAgent-based direct movement remains an engineering hypothesis to validate, not an irrevocable requirement.

### Left Mouse Button — Basic Attack

**Approved behavior: each deliberate LMB click requests one individual basic attack.**

Requirements:

- One click requests one attack, not an entire automatic combo.
- Subsequent clicks can advance the existing weapon-specific combo sequence.
- Preserve authored cadence, animation timing, impact events, recovery, cancel windows, hitstop, and enemy reactions.
- Respect existing attack eligibility and busy states.
- Do not introduce accidental double attacks or uncontrolled input buffering.
- Do not trigger attacks through old click-to-move behavior.
- Each weapon retains its own attack sequence and identity.

Holding LMB to repeat attacks is **not yet approved as the final control policy**.

Audit its current behavior and compatibility. Do not silently preserve or remove it; propose the safest migration policy, keeping the explicitly approved one-click/one-request default.

### Right Mouse Button — Weapon-Specific Special

**Approved behavior: RMB activates the unique special mechanic of the equipped weapon.**

RMB is:

- NOT an alternative basic attack.
- NOT simply a replacement for the final hit of an LMB combo.
- NOT a fifth modular skill.
- NOT a substitute for one of the Q/E/R/X slots.

For Gauntlet, RMB must become the input for the **existing Asura mechanic**.

Before designing its migration, inspect:

- Existing Asura activation and execution ownership.
- Resource generation and consumption.
- Stages, continuations, and early finishes.
- Cooldowns, if applicable.
- Animation and presentation.
- Hit timing, damage, and reactions.
- Interruptions, cancellation, pause, hitstop, and cleanup.
- Existing F11 or custom input binding behavior.

Reuse the actual Asura implementation. Do not create another Asura executor or simplify the mechanic to fit the new input scheme.

Spear and Bow must eventually have their own meaningful weapon-specific RMB mechanics. Audit their current capabilities, but do not invent or implement new weapon kits during GPR-C01.1.

### Modular Active Skills

The approved target scheme is:

- Q: Active Skill Slot 1.
- E: Active Skill Slot 2.
- R: Active Skill Slot 3.
- X: Active Skill Slot 4.

Maintain the existing internal slot indices where compatible.

Distinguish physical key bindings from internal ability IDs and execution logic.

Do not replace or remove the current Gauntlet finisher, contextual finishing behavior, or Asura continuation during this migration.

Audit the exact ownership and input relationships of these existing actions before assigning new defaults.

### Interactions and contextual actions

- Space for dodge is the approved target default.
- Pause remains Esc unless compatibility requires explicit review.
- F for contextual finishing is provisionally preserved.
- The default interaction key is not yet approved.
- Other auxiliary bindings require an explicit compatibility decision.

Do not silently assign new bindings that conflict with existing skills, interactions, or contextual actions.

### User-configurable bindings

The finished control system must allow players to remap relevant keyboard and mouse actions through Settings.

The GPR-C01 design must include:

- Action-based input mapping.
- Binding conflict detection.
- Appropriate reserved-key handling.
- Persistence across sessions.
- Restoring defaults.
- UI/HUD labels reflecting actual bindings.
- Safe handling of legacy player preferences.
- Input blocking while menus or modal interfaces own control.
- Correct input release and held-button behavior.
- No duplicate execution from overlapping action maps.

Do not implement this settings system during GPR-C01.1.

## 4. Preserve existing combat foundations

The migration must preserve the validated gameplay behavior developed in the earlier Gameplay Intelligence iterations.

In particular:

- Gauntlet impact timing and attack cadence.
- Q/W/E presentation synchronization.
- Existing damage and hit-confirmation ownership.
- Enemy flinch, Push, Stagger, and interruption policies.
- Cancel rules and execution priorities.
- Hitstop, pause, recovery, and cleanup.
- Existing dash and skill movement semantics.
- Asura resource and execution contracts.
- Protocol and Mutation compatibility.
- RunSummary damage attribution.
- Bow and Spear existing behavior where migration affects them.

Do not rewrite the combat engine merely to change inputs.

Avoid introducing parallel input, movement, ability, or damage pipelines.

## 5. Current implementation authorization

Their purpose is to establish baselines and prepare the control migration.

Do not implement:

## 7. GPR-C01.1b — Migration design and readiness

Based on the baseline, produce an implementation-ready technical design.

It must describe:

- The recommended architecture for WASD movement.
- Whether the existing NavMeshAgent can provide satisfactory direct control.
- Alternative movement approaches if the current solution fails its prototype criteria.
- Separation of direct movement, aiming, targeting, and skill-driven movement.
- How one-click/one-basic-request will integrate with existing attack execution.
- How RMB will activate Asura without modifying its execution.
- The slot-binding migration to Q/E/R/X.
- Handling of legacy controls and user-defined bindings.
- Settings and rebinding implementation.
- Animation, facing, dash, and combat commitment rules.
- UI ownership and safe input suppression.
- Expected changes to the three weapons.
- Test plan and regression coverage.
- Human playtest and acceptance criteria.
- Minimal implementation steps with explicit dependencies.

Update ADR-0006, requirements, design, and tasks to match the approved decisions.

Do not present unresolved design options as approved decisions.
